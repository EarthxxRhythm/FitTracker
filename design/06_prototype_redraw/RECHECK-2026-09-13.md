## 九、首个真实视觉修复与复测（2026-09-13）

### 9.1 login：9.79% → 5.97%（达标）

**这是本轮第一次真实的视觉缺陷修复**（此前只有测量与基线）。

**定位方法（剖面法，避免逐条猜 CSS）**：对原型帧与设备截图做逐行亮度剖面 + 文字行区间提取，把 13 个元素一一对齐。

对齐结果：前 8 行差值稳定在 **36–43vp**（= 全局对齐量；align 35 与真值差约 3vp），从「记住我」到「登录按钮」**骤增到 81vp**，其后稳定在 82–84vp 不再增长——说明是**局部**缺失，而非整体错位。

逐段核算间距：原型「记住我」底→按钮顶 = **45vp**，设备 = **18vp**。

**根因（原型 CSS）**：
- `.auth-cta { margin-top: 20px }` —— 登录按钮上方额外 20px
- `.auth-aux { margin-top: 2px }` —— 「记住我」行额外 2px

ArkUI 侧两者都只是 `Column({ space: 14 })` 的普通成员、无额外 margin，故该段比原型矮 22vp（实测 27vp，残差来自行高差异）。

**修复**（`entry/src/main/ets/features/pencil/pages/PencilLoginPage.ets`，commit `2ea9813`）：
- 登录 Button 加 `.margin({ top: 20 })`
- `buildAuthAux()` 的 Row 加 `.margin({ top: 2 })`

**复测**（同口径：`--crop 100,740` + a11y 文本掩码）：

| align | 修复前 | 修复后 |
|---|---|---|
| 30 | — | **5.98%** |
| **35** | **9.79%** | **5.97%** ✅ |
| 40 | 10.40% | 7.41% |

分带对比（align 35）：band 6（384–448）由 **32.94% → 1.43%**。

**残留**：band 7（448–512）仍 30.60%——该屏还有第二处未修差异（疑在「其他登录方式」分隔线或社交按钮区），留待下轮。

### 9.2 复测的导航障碍与解法（重要）

复测时发现：splash 已改为免登录直达主界面，**welcome / login / register 三屏从启动流不可达**，无常规导航路径可复测。

解法（临时、已复原）：把 splash 分支内的**目标路由**临时改为 `WELCOME`。
> **踩坑**：不能在条件上写 `&& false` —— 那会破坏 TS 类型收窄，`context` 退回 `Context | null`，编译报 `Argument of type 'Context | null' is not assignable to parameter of type 'Context'`。必须改的是分支体内的路由目标。

复测后已改回 `APP_SHELL`；`git diff` 该文件为空，工作区无残留。

**这暴露一个长期问题**：认证三屏现在**没有任何可达入口**。若要继续验收或让用户能登录，需在「我的」或设置页补入口。

### 9.3 seed 修正：计划由「清空」改为「真实生成」

`DeviceSeedService` 两处 `replaceMyPlans(context, [], '')` → `enablePlan(context, 'preset_upper_lower')`（同 commit `2ea9813`）。

原 seed 从不生成计划（两处都显式清空），是 home「动作数 0 / 预计用时 0 / 目标肌群 0」与 plan 屏空的根因。改用 `TrainingPlanService.enablePlan` 走真实预设生成，符合 8.2 裁定 (a) 路（真实生成，非硬编码示例数字）。

实测：首页进度环 **0% → 67%**；profile 9.71% → **9.48%**。

**注**：home 的「动作数 0」在周日仍为 0 —— `preset_upper_lower` 的训练日是 `[1]`~`[5]`（周一至周五），周日为休息日，`getTodayTraining` 返回 null。这是**产品真实行为**而非缺陷，属 8.2 的数据差范畴，应登记豁免而非造数据。


## 十、口径缺陷更正与两屏重判（2026-09-13，galaxy collect-audit 维度产出，协调者已核实）

### 10.1 工具缺陷：掩码 align 与 compare align 不一致

`tools/collect-screens.ps1` 原实现对**所有屏**一律用 `genmask <dump> 35` 生成掩码，再按 `--align-y 0/20/35/45` 扫描。**扫到 0 时掩码仍按 35 偏移**，两者错位 35vp → 文本未被真正掩住 → 指标虚高。

实测（library 屏）：

| 掩码生成 align | compare align | 超阈% |
|---|---|---|
| 35 | 0 | 28.42（= 原登记值） |
| 0 | 0 | **26.73**（自洽） |

**影响面**：§6 表中所有「@align 0」类数字都带同样偏差。**已修正脚本**（掩码改为与本轮 align 同值，L83）。

### 10.2 library 重判：掩蔽媒体后达标

媒体带几何由 a11y + 原型 CSS 推导，非臆测：卡片外框取自 a11y 的 `Column#lib-card-<id>`；媒体带高度 = 卡宽 × 3/4（原型 `.lib-media { aspect-ratio: 4/3 }`）。

> ⚠ a11y 中卡内的 `Column [304,824,406,926]`（102×102px）**只是媒体区中央的 fallback 图标，不是媒体带**——只掩它会漏掉整个 GIF 区。

自洽口径（掩码 align == compare align）：

| align | 文本掩码 only | 文本 + 媒体掩码 |
|---|---|---|
| −16 | 20.68 | 5.66 |
| **−12** | 19.50 | **3.75**（MAE 6.43） |
| 0 | 26.73 | 6.72 |
| 35（物理锚点） | 44.85 | 15.27 |

**结论**：
