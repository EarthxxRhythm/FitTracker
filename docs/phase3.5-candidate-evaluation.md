# FitTracker Phase 3.5 候选评估

更新时间：2026-06-03

## 1. 评估范围

本文聚焦两类 `phase3.5` 候选：

1. 本地备份/恢复
2. 动作详情媒体化演进

结论基于当前仓库实现，不假设额外后端、账号体系或云同步能力。

## 2. 当前数据层盘点

### 2.1 用户数据

| 数据类型 | 当前落地方式 | 位置 | 进入备份建议 |
| --- | --- | --- | --- |
| 训练目标 `goal` | Preferences | `GoalRepository` | 必须 |
| 我的计划 `plan` | Preferences | `TrainingPlanService` | 必须 |
| 当前计划指针 | Preferences | `TrainingPlanService` | 必须 |
| 训练记录 `session` | Preferences | `WorkoutSessionService` | 必须 |
| 训练草稿 `draft` | Preferences，本地恢复可用 | `WorkoutDraftService` / `HomePage` | 暂不进入，先不纳入备份 schema |

### 2.2 内容数据

| 数据类型 | 当前落地方式 | 位置 | 进入备份建议 |
| --- | --- | --- | --- |
| 动作种子内容 | JSONL -> 运行时导入 RDB | `content/exercises/*.jsonl`、`ContentDatabaseService` | 不备份原始内容 |
| 内容数据库 | `fittracker_content.db` | `ContentDatabaseService` | 不建议整库备份 |
| 内容同步状态 | 占位实现 | `SyncService` | 可只备份轻量版本号 |
| 视频/封面地址 | 内容字段内维护 | `videoUrl` / `coverUrl` | 不备份缓存，备份引用即可 |

## 3. EntryBackupAbility 现状判断

当前仓库已经具备“可以接入”的入口，但还不能算“可交付的备份能力”。

### 已有基础

- `module.json5` 已注册 `EntryBackupAbility`
- `backup_config.json` 已允许备份恢复
- `EntryBackupAbility.ets` 已实现 `onBackup()` / `onRestore()` 生命周期

### 当前缺口

- 只有日志，没有导出、导入、校验、冲突处理
- 没有定义备份数据结构和 schema version
- 没有区分“用户数据”和“可重建内容数据”
- 没有恢复后的重建动作，例如：
  - 当前计划指针修复
  - 重复 session 去重
  - 内容版本不一致时的回退策略

### 结论

`EntryBackupAbility` **适合作为后续挂载点**，但**不适合作为 phase3.5 首个落地形态**。  
原因很简单：现在最缺的不是系统入口，而是可验证的数据协议与恢复规则。

另外，回顾页已经具备“目标调整建议 -> 调整后预览 -> 保存”的体验闭环，说明当前产品更值得优先补齐的是数据导入导出与恢复规则，而不是继续把 phase3.5 时间花在额外的目标调整页面重构上。

## 4. 本地备份/恢复可行路径

## 4.1 路径 A：应用内手动导出/导入 JSON 包

### 方案

把用户自产数据导出为一个受版本控制的 JSON 包，例如：

```json
{
  "schemaVersion": 1,
  "exportedAt": 1780365600000,
  "goal": {},
  "plans": [],
  "currentPlanId": "",
  "sessions": [],
  "contentMeta": {
    "contentVersion": 1
  }
}
```

### 优点

- 不依赖系统恢复链路，验证成本最低
- 数据范围清晰，便于做增量兼容
- 更适合当前“本地优先、无账号、无云端”的产品状态
- 后续仍可复用同一份 schema 给 `EntryBackupAbility`

### 风险

- 需要设计导入时的冲突规则
- 需要处理跨版本字段兼容
- 用户要主动执行导出动作

### 结论

**这是最值得进入 phase3.5 的路径，也是推荐优先级第 1。**

## 4.2 路径 B：系统级备份/恢复（基于 EntryBackupAbility）

### 方案

在 `EntryBackupAbility` 内复用与路径 A 相同的数据结构，由系统触发备份和恢复。

### 优点

- 用户感知更弱，迁移体验更自然
- 能与系统备份能力对齐

### 风险

- 测试面更大，依赖系统恢复场景
- 出问题时定位难度高于手动导入
- 如果先做系统级能力，恢复失败会直接暴露为“用户数据丢失”

### 结论

**可以做，但建议排在手动导入/导出之后。**  
适合作为 `phase3.5` 尾项或 `phase4` 首项。

## 4.3 路径 C：整库备份（含内容数据库和媒体缓存）

### 结论

**不建议进入 phase3.5。**

原因：

- 内容种子可重建，重复备份收益低
- RDB 内容会随着内容版本变化而重建
- 媒体缓存体积不可控
- 容易把“用户数据恢复”问题扩展成“内容同步和资产一致性”问题

## 5. 备份数据范围建议

### 必须备份

1. `goal`
2. `my_plans`
3. `current_plan_id`
4. `sessions`

### 建议备份

1. 内容版本号或内容来源标记
2. 导出时间
3. schema version

### 暂不备份

1. `fittracker_content.db` 的动作内容明细
2. 视频/封面缓存文件
3. 训练草稿快照与其中间态
4. 可由内容种子重新生成的数据

## 6. 恢复流程风险

### 6.1 数据冲突

典型场景：

- 当前设备已有 session，导入包里也有 session
- `current_plan_id` 指向的计划在导入结果中不存在

建议规则：

- session 按 `id` 去重
- plan 恢复后若当前计划缺失，回退到最近启用计划
- goal 采用“导入包覆盖本地”即可，复杂度最低

### 6.2 版本兼容

当前数据结构还在演进，尤其训练编辑和草稿链路未稳定。  
因此备份包必须自带 `schemaVersion`，并预留迁移入口。

### 6.3 内容版本错位

用户数据依赖动作 ID、计划 ID、session 内动作名称。  
如果未来内容库更新导致动作详情变化，恢复用户训练记录时可能出现：

- 历史记录能显示，但跳转不到最新动作详情
- 替代动作关系变化

建议：

- 历史 session 视为“事实记录”，不因内容变更而重写
- 恢复后若内容库缺失动作详情，优先显示历史文本，不阻断记录查看

### 6.4 草稿恢复边界

当前首页已经有“恢复训练”入口，`WorkoutDraftService` 也能把训练过程快照持久化到 Preferences。  
但这还不等于草稿已经适合纳入备份：它仍然缺少跨版本迁移策略、导入冲突规则，以及和正式训练记录之间的恢复优先级定义。

结论：**草稿已经完成应用内恢复闭环，但进入备份前仍应先补版本兼容与冲突策略。**

## 7. 是否值得进入 Phase 3.5

### 备份/恢复

**值得进入，但要缩成 MVP。**

推荐顺序：

1. 手动导出/导入用户数据
2. 冲突处理与版本迁移
3. 再评估是否接入 `EntryBackupAbility`

不建议在 `phase3.5` 同时做：

- 系统级恢复
- 草稿恢复
- 内容整库恢复
- 媒体缓存恢复

## 8. 动作详情媒体化演进建议

## 8.1 当前判断

当前仓库已经为动作详情预留了媒体字段与内容数据库结构，但媒体能力还不稳定：

- `videoUrl` / `coverUrl` 已存在
- 内容文档已要求只使用自制、授权或开放许可资源
- `SyncService` 仍是占位实现，说明远端拉取和缓存体系未完成
- 现有 JSONL 中部分视频地址仍是 `local://` 占位，且部分内容文本还存在乱码/占位值

因此，**phase3.5 不应把“接播放器”当成第一步，而应先把媒体资源治理做完整。**

## 8.2 是否接播放器

### 建议

**接，但只接轻量播放器，不做复杂播放体系。**

适合 phase3.5 的范围：

- 动作详情页播放单个短视频
- 支持封面图、加载失败、无资源占位
- 支持本地资源和受控远端 URL

不适合 phase3.5 的范围：

- 多清晰度切换
- 大规模预下载
- 后台批量缓存
- 自动播放整页动作流

## 8.3 资源来源建议

只接受以下来源：

1. 自制拍摄
2. 已签约授权素材
3. 许可明确的开放资源

必须在内容数据层保留：

- `license_type`
- `source_note`
- `checksum`
- 资源版本号

不允许：

- 接 MuscleWiki 官方 API
- 抓取第三方页面视频、图片、文案
- 把来源不清晰的短视频直接打进包内

## 8.4 缓存建议

### phase3.5 建议

- 本地内置演示资源：少量、可控
- 远端资源：按需播放，不做全量预缓存
- 最多做小体积临时缓存和手动清理入口

### 不建议现在做

- 离线缓存全动作库视频
- 首次安装后预拉整批媒体
- 把缓存可靠性和用户数据恢复绑在一起

## 8.5 包体风险

视频是最容易把 HAP 包体做胖的部分。  
如果 phase3.5 直接内置大量 MP4，会带来：

- 安装包膨胀
- 构建产物增大
- 更新成本变高
- 低端设备存储压力上升

建议：

- 包内只保留 3 到 5 个演示级短视频用于联调或首屏体验
- 大部分正式素材转向受控远端资源或后续下载包

## 8.6 版权风险

这是媒体能力里最高优先级的风险项。

如果资源授权链不清楚，播放器做得再顺也不该上线。  
所以媒体化正确顺序不是“先播起来”，而是：

1. 先确认来源合法
2. 再固化元数据
3. 再接播放器
4. 最后再谈缓存和分发

## 9. 推荐排序

### 推荐进入 phase3.5

1. 用户数据手动导出/导入
2. 备份包 schema 与冲突处理
3. 动作媒体元数据治理
4. 动作详情轻量播放器

### 建议延后

1. 系统级自动备份/恢复
2. 训练草稿恢复
3. 内容整库备份
4. 媒体批量缓存
5. 多资源形态播放器

## 10. 最终结论

### 关于本地备份/恢复

值得做，但应该把目标定为“恢复用户成果数据”，而不是“复制整个本地环境”。  
当前最可行路径是：**先做手动导出/导入 JSON 包，再把同一套数据模型接入 `EntryBackupAbility`。**

### 关于动作详情媒体化

值得推进，但 phase3.5 的正确切入点是“资源治理 + 轻量播放”，不是“大规模离线视频”。  
当前最稳妥顺序是：**先清理授权和元数据，再接单视频播放器，缓存与大规模素材分发后置。**
